# Chapter 02 소프트웨어 개발 프로세스

---

## Section 01. 소프트웨어 개발 프로세스의 이해

### 1. 프로세스란?
- **일을 처리하는 과정 또는 순서**
  - 예) 공장에서 자동차, 세탁기 등이 조립되어 완제품이 되는 과정
  - 예) TV 요리 프로에서 요리사가 맛있는 요리를 만드는 과정

### 2. 프로세스의 정의
- 주어진 일을 해결하기 위한 목적으로 그 순서가 정해져 수행되는 **일련의 절차**

### 3. 소프트웨어 개발 프로세스의 목적
- 이전에 얻은 **노하우를 전달** → 시행착오 감소 → 빠르게 적응
- **가이드(guide) 역할** 수행
- 프로세스의 3요소: **인원 × 프로세스 × 도구와 장비**

## Section 02. 소프트웨어 프로세스 모델의 이해

### 1. 소프트웨어 개발 규모에 따른 비유
| 규모 | 비유 |
|------|------|
| 작은 규모 | 개집 짓는 일 |
| 대규모 | 빌딩 짓는 일 |

### 2. 소프트웨어 개발 생명주기 (SDLC)
- **Software Development Life Cycle**
- SW를 어떻게 개발할 것인가에 대한 **전체적인 흐름을 체계화**한 개념
- 개발 계획 수립부터 최종 폐기까지의 전 과정을 다룸
- 순차적인 단계로 이루어짐

### 3. 소프트웨어 프로세스 모델의 목적
- 소프트웨어 개발의 전 과정을 하나의 프로세스로 정의
- 주어진 예산과 자원으로 개발하고 관리하는 방법을 구체적으로 정의
- **고품질의 소프트웨어 제품 생산**을 목적으로 함

## Section 03. 주먹구구식 모델 (Build and Fix)

### 1. 개요
- **Build and Fix 모델** / Code and Fix 모델 / 즉흥적 소프트웨어 개발 모델
- 공식적인 가이드라인이나 프로세스가 **없는** 개발 방식
- 요구 분석 명세서나 설계 단계 없이 간단한 기능만 정리하여 개발

### 2. 개발 단계
```
코딩(구현) → 제품 → 문제? → [아니오] → 사용
                 ↑              [예]
                 └── 수정 ──────┘
```

### 3. 적합한 상황
- 개발자 한 명이 단시간에 마칠 수 있는 경우
- 대학 수업의 한 학기용 프로젝트 정도

### 4. 단점
- 정해진 개발 순서나 문서화된 산출물이 없어 **관리 및 유지보수 어려움**
- 프로젝트 전체 범위 파악 불가, 좋은 아키텍처 구성 불가
- 업무 분담 및 진척 상황 파악 불가
- 계속적 수정으로 프로그램 구조가 나빠져 **수정이 매우 어려워짐**

## Section 04. 선형 순차적 모델 (폭포수 모델)

### 1. 개요
- **Linear Sequential 모델** / Waterfall 모델 / Classic Life Cycle
- 계획 → 요구 분석 → 설계 → 구현 → 테스트 → 유지보수 순으로 진행
- 각 단계마다 **검증(검토)** 수행

### 2. 개발 단계
```
계획 → 요구 분석 → 설계 → 구현 → 테스트 → 유지보수
 ↓         ↓         ↓       ↓        ↓
개발     요구사항   설계    모듈별   테스트
계획서   정의서/    사양서   코드
        명세서
```

### 3. 장점
- **관리 용이**
- **체계적인 문서화**
- 요구사항의 변화가 적은 프로젝트에 적합

### 4. 단점
- 각 단계는 앞 단계가 완료되어야 수행 가능 (순차적 구조)
- 각 단계의 결과물이 완벽해야 다음 단계에 오류 없이 진행 가능
- 사용자가 중간에 **가시적인 결과를 볼 수 없어** 답답함

---

## Section 05. V 모델

### 1. 개요
- **폭포수 모델 + 테스트 단계 추가 확장**
- 폭포수 모델: 산출물 중심
- V 모델: **각 개발 단계를 검증하는 데 초점**

### 2. 구조
```
요구 분석 ─────────────────────────── 시스템 테스트 → 인수 테스트
    ↓          요구 분석 검증               ↑
  아키텍처 설계 ───────────────── 통합 테스트
       ↓          인터페이스 검증       ↑
     모듈 설계 ──────────── 단위 테스트
          ↓      모듈 검증      ↑
               구현 ──────────┘
```

## Section 06. 진화적 프로세스 모델

### 1. 등장 배경
- 선형 순차적 모델(폭포수)의 한계를 보완하기 위해 등장
- 대표 모델: **프로토타입 모델**

### 2. 프로토타입이란?
- 대량 생산에 앞서 미리 제작해보는 **원형 또는 시제품**
- 소프트웨어 개발에서: 완전한 SW 개발 전 사용자 요구를 받아 **모형을 만들고 의사소통 도구로 활용**

### 3. 프로토타입 모델의 개발 생명주기
```
[폭포수 모델]  계획 → 요구사항 정의/분석 → 설계 → 구현 → 테스트 → 유지보수

[프로토타입]  요구 수정 → 빠른 설계 → 프로토타입 개발 → 고객 평가 → 프로토타입 조정 → 구현
```

### 4. 실험적 프로토타입 모델
```
요구 분석 → 빠른 설계 → 프로토타입 개발 → 고객 평가
                ↑                               |
                └─── 수정 요구 사항 ←── [아니오]  |
                                       [예] → 최종 사용자 요구 → 분석 → 설계 → 구현
```

### 5. 프로토타입 개발 단계
1. **요구사항 정의 및 분석**: 1차 개략적 요구 → 반복 수정하며 최종 프로토타입 완성
2. **프로토타입 설계**: 사용자와 대화 가능한 수준의 설계 (입출력 UI 중심)
3. **프로토타입 개발**: 완제품이 아닌, 사용자 요구 항목 및 출력 결과 확인용

## Section 09. 통합 프로세스 모델 (UP)

### 1. 등장 배경
- 폭포수 모델의 문제점 → **반복적 개발 방법**으로 해결

### 2. 통합 프로세스(UP: Unified Process) 모델
- 도입 → 구체화 → 구축(반복) → 전이의 4단계로 구성
- 각 단계에서 **비즈니스 모델링, 요구사항 정의, 분석/설계, 구현, 테스트, 배치** 등이 병행

### 3. UP 모델의 4단계

| 단계 | 영문 | 주요 활동 |
|------|------|-----------|
| 도입 | Inception | 프로젝트 범위 정의, 초기 요구사항 파악 |
| 구체화 | Elaboration | 아키텍처 설계, 요구사항 구체화 |
| 구축 | Construction | 반복적 구현 및 테스트 (n번 반복) |
| 전이 | Transition | 배포, 사용자 인수 |

### 4. 공통 작업 (전 단계 수행)
- 형상(변화) 관리
- 프로젝트 관리
- 환경 점검

### 5. 비즈니스 모델링
- 소프트웨어 개발에 앞서 **비즈니스 환경을 이해하고 분석**하는 핵심 작업
- 프로젝트 초기(도입 및 구체화 단계)에 집중적으로 수행
- 주요 역할:
  - 시스템 목적 및 범위 정의
  - 현실 세계의 개념화 (도메인 모델 구축)
  - 업무 프로세스 분석 (BPMN 등 활용)
  - 이후 요구사항 정의·설계 단계의 **기반 제공**

> **BPMN (Business Process Model and Notation)**: 조직 내 업무 흐름을 시각화하고 표준화하기 위한 글로벌 그래픽 표기법

## Section 10. 애자일 프로세스 모델

### 1. 개요
- **Agile**: '날렵한', '민첩한'
- 고객의 요구에 **민첩하게 대응**하고 그때그때 주어지는 문제를 풀어나가는 방법론

### 2. 애자일 선언문 (핵심 가치)
| 기존 방식 | → | 애자일 가치 |
|-----------|---|-------------|
| 프로세스·도구 중심 | → | **개개인과의 상호 소통** 중시 |
| 문서 중심 | → | **실행 가능한 소프트웨어** 중시 |
| 계약·협상 중심 | → | **고객과의 협력** 중시 |
| 계획 중심 | → | **변화에 대한 민첩한 대응** 중시 |

### 3. 개발 방법
- 반복적인 개발을 통한 **잦은 출시**를 목표
```
프로토타입 개발 → 사용자 확인 → 일부 기능 사용
```

### 4. 스크럼 (Scrum)
- 팀의 개선과 프로젝트 관리를 위한 애자일 방법론
- **경험적 관리 기법** 중 하나
- 구체적인 프로세스를 명확하게 제시하지 않음
- 개발 팀을 운영하는 **효율적인 운영 방식(지침)**

> "팀원들이 럭비의 스크럼처럼 똘똘 뭉쳐서(Scrum), 짧은 구간을 전력 질주(Sprint)하며 목표를 달성한다"

#### 스크럼 진행 과정
```
① 제품 기능 목록 작성 (Product Backlog)
② 스프린트 계획 회의 → 스프린트 구현 목록
③ 스프린트 수행 (1~4주)
   - 스크럼 마스터 주관
   - 매일 일일 스크럼 회의
   - 소멸 차트로 진행 추적
④ 스프린트 개발 완료 → 최종 제품
⑤ 스프린트 완료 후: 스프린트 검토 회의 + 스프린트 회고
```

## 주요 모델 비교 요약

| 모델 | 특징 | 장점 | 단점 |
|------|------|------|------|
| 주먹구구식 | 계획 없이 코딩 후 수정 | 빠른 시작 | 유지보수 불가, 구조 붕괴 |
| 폭포수 | 순차적 단계 진행 | 관리 용이, 문서화 | 변경 어려움, 중간 결과 없음 |
| V 모델 | 폭포수 + 단계별 검증 | 테스트 강화 | 변경에 유연하지 않음 |
| 프로토타입 | 시제품 제작 후 반복 개선 | 요구사항 명확화 | 관리 어려움 |
| 통합 프로세스(UP) | 반복+점증적 개발 | 유연성, 위험 조기 감소 | 복잡한 관리 |
| 애자일/스크럼 | 민첩한 반복 개발 | 변화 대응, 고객 협력 | 문서화 부족 가능 |
